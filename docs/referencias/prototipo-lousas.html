Trecho do artigo

Chave de idempotência

Um cliente pede uma cobrança, a rede falha no caminho de volta e ele tenta de novo. Se a API não souber reconhecer que é o mesmo pedido, cobra duas vezes. A solução vem de três peças: uma chave enviada pelo cliente, uma restrição única no banco e a resposta guardada.

A chave, a restrição e a resposta

Role devagar: a lousa acompanha a leitura e o desenho avança um passo a cada parágrafo. Rolando de volta, ele se apaga.

O cliente pede uma cobrança e manda junto uma chave de idempotência gerada por ele, abc-123. A chave é a mesma em todas as tentativas desse pedido.

Antes de cobrar, a API grava a chave numa tabela com restrição UNIQUE. Quem grava primeiro fica com a chave, e o estado começa como em andamento.

A API cobra no adquirente e guarda a resposta junto da chave. Agora a tabela sabe o resultado: concluída, 201.

A resposta se perde no caminho de volta. Para o cliente é como se nada tivesse acontecido, então ele tenta de novo, com a mesma chave.

O INSERT da segunda tentativa bate na restrição UNIQUE. Em vez de cobrar de novo, a API devolve a resposta que já estava guardada.

Depois do diagrama, o texto segue normalmente. As outras figuras de explicação (a de arrastar e a animação curta) usariam a mesma lousa.
